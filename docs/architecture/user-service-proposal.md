# User Service Proposal

**Status** Proposed future work

Second Memory needs a way to admit users gradually and limit the model credits they can spend when the app is published. Add a `user-service` that combines identity, account access, and usage limits. This work can be planned independently of the [AWS migration](aws-migration-plan.md).

Today, Memory and Ask use shared NestJS auth code that verifies a Firebase ID token and can create a user and tenant during a normal API request. A valid Firebase sign-in is enough to start using the product. [Current auth flow](../../packages/nest-auth/src/firebase-auth.service.ts)

## Service and database ownership

Firebase handles sign-in. User Service owns the mapping from Firebase UID to Second Memory's `userId` and `tenantId`, as well as tenant membership, account status, invitations, and usage limits. Keep these responsibilities in modules within one service so account activation and allowance checks can use the same database.

Each service that uses PostgreSQL owns its database, Prisma schema, client, and migrations. Memory owns entries and embeddings. Ask owns conversation state in its own store. Memory and Ask use the internal IDs issued by User Service and access other services' data through their APIs. When moving identity records, preserve existing user and tenant IDs and replace Memory's current foreign keys to the identity tables with UUID references resolved through User Service. [Current Prisma schema](../../packages/server-db/prisma/schema.prisma)

## Invitations and waitlist

- A user signs in with Firebase and registers with User Service. Registration creates a `pending` account, and the web and mobile apps can show its status.
- A valid invitation or an operator's approval makes the account `active`. Redeem the invitation and activate the account in one transaction so a single-use invitation can activate only one account.
- Require `active` status for normal Memory and Ask requests.

## Request flow and row access

1. The client calls Memory or Ask with a Firebase ID token. The receiving service calls User Service over an authenticated internal connection. User Service verifies the token, resolves the UID to the internal IDs, and checks account status. For a paid operation, it can reserve the allowance in the same request.
2. When Ask calls Memory for retrieval or to save a summary, it forwards the verified user and tenant context over an authenticated service-to-service call. Memory scopes the operation to that context.
3. Memory sets the verified IDs as transaction-local PostgreSQL settings and queries through the same Prisma transaction client. PostgreSQL row-level security (RLS) matches both `tenantId` and `userId` for private entries. Embeddings and other entry-owned rows follow the parent entry's access rules. Data intentionally shared across the tenant can use a tenant-only policy. Use a runtime database role subject to RLS and a separate role for migrations.

## Daily usage limits

Start with configurable daily per-user action limits for Ask messages and memory captures. Include the conversation summary generated by Ask's end-session action in the allowance policy because it also uses the model. Active users who exhaust an allowance can still read saved memories. Return the reset time so the apps can tell users when paid actions are available again. [Ask generation paths](../../services/ask-service/src/ask/ask.service.ts) · [Memory embedding paths](../../services/memory-service/src/memories/memories.service.ts)

Reserve allowance atomically before the first paid call, including retrieval embeddings. Use a stable operation ID so retries reuse the same reservation. Carry that ID through internal calls and any queued work. Reuse completed results where possible. If a provider timeout leaves the outcome unknown, account for the possible charge before retrying.

Per-user limits bound each account's usage. If launch also needs a service-wide credit ceiling, reserve against a shared daily budget using a cost bound for each operation and reconcile against provider usage. One Ask message can consume a retrieval embedding and an LLM call, while ending a session can consume a summary call and an embedding. Count each user action once in the daily action limit and account for all its provider calls in the credit budget.

## Open decisions

- Choose the initial daily allowances, reset timezone, and how to charge for attempts that fail after consuming provider credits.
- Choose who can create invitations or approve accounts, how long invitations last, and which existing accounts start active.
- Decide whether launch requires a shared credit ceiling and where each provider reports usage for reconciliation.

## Launch checks

- A signed-in pending account can check its status. Direct calls to Memory and Ask are denied until activation.
- Under concurrent requests, only one operation can claim the final allowance unit. Retrying that operation does not increase its usage count.
- Existing memories remain reachable by their original owners. Different tenants and different users within the same tenant cannot read one another's private entries or embeddings.
- Check every reachable API deployment before publishing, including any older endpoint that can still initiate paid work.
